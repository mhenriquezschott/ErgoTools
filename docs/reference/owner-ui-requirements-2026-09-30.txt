## 2. Refactor the UI implementation, do NOT redesign the UI

The fact that the visual UI must remain unchanged does NOT mean that the existing UI code should simply be copied as-is.

Quite the opposite.

I expect the existing UI code to be reused as the reference and starting point, but migrated and improved according to the new architecture. This includes:

- cleaning up the code
- standardizing it
- documenting it
- testing it
- separating presentation/UI code from business logic
- separating calculations from visual components
- removing duplicated code
- fixing inappropriate dependencies
- fixing circular calls or problematic signal/event interactions
- improving error handling
- improving robustness
- improving responsiveness where possible
- improving resize behavior
- improving compatibility across Windows, Linux, and macOS
- organizing shared UI functionality appropriately
- making the UI implementation conform to the new coding standards and architecture

In other words:

THE INTERNAL IMPLEMENTATION OF THE UI CAN AND SHOULD IMPROVE.

THE FINAL VISUAL APPEARANCE AND USER WORKFLOW SHOULD NOT CHANGE.

These are two different things.

The existing UI is not arbitrary.

Therefore, do NOT interpret this migration as an opportunity to "modernize," simplify, reorganize, or redesign the interface based on your own assumptions about what would make a better UI.

The objective of this migration is primarily to improve the SOFTWARE ARCHITECTURE, CODE QUALITY, MAINTAINABILITY, TESTABILITY, DOCUMENTATION, DEPENDENCY MANAGEMENT, and PLATFORM COMPATIBILITY while preserving the established user experience.

## 5. Limited UI changes that ARE allowed

There are some exceptions where UI-related changes are acceptable as part of this migration.

For example:

- adding or reorganizing items in the main top menu when required by the new architecture or application-wide features
- improving the application Settings/Configuration window, which is currently very limited
- fixing actual UI bugs
- fixing incorrect interlocks between controls
- fixing recursive or looped signal/event calls
- fixing resizing problems
- fixing layout behavior that breaks under different resolutions, DPI settings, or operating systems
- improving Windows/macOS/Linux compatibility
- improving responsiveness or preventing the UI from freezing unnecessarily
- improving robustness when errors occur
- removing redundant UI implementation code when doing so does not change the resulting interface
- making internal changes required to support multilingual UI and metric/imperial units

However, these are implementation and robustness improvements, NOT authorization for a visual redesign.

If you identify a UI change that you believe would genuinely improve usability, such as moving a button, adding a new control, reorganizing a panel, changing a workflow, or modifying a layout, DOCUMENT IT as a potential future improvement.
